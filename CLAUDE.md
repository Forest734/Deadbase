# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Deadbase is a Grateful Dead setlist browser: an Express 5 JSON API plus a
no-build vanilla-JS front end in `public/`. Hand-assembled in the shape of
`~/dev/Hawk` (node-api + web-static), not generated by `new-project.sh`.

## Commands

```sh
npm install
npm run dev                          # http://localhost:3000 (PORT overrides), node --watch
npm test                             # node:test, all files in tests/
node --test tests/app.test.js        # one file
node --test --test-name-pattern="Cornell" tests/app.test.js   # one test
npm run import -- <gdshowsdb clone>  # regenerate data/shows.json
```

No linter, formatter, or build step. `node --check public/main.js` catches front-end syntax errors;
the tests only cover the API, so front-end changes need checking in a browser (or jsdom).

## Architecture

**Data pipeline.** `scripts/import-gdshowsdb.js` reads the per-year YAML from
[gdshowsdb](https://github.com/jefmsmit/gdshowsdb) (MIT) and writes
`data/shows.json`, which is committed. The app never touches the network. `js-yaml` is a
devDependency used only by the importer. Source keys are `YYYY/MM/DD`, or `YYYY/MM/DD/N`
when there were several shows that day; show ids are the ISO date, plus `-N` in that case. Ids sort
chronologically, and the order of everything else depends on that.

**`src/data.js` is the whole model.** At import time it loads the JSON once and enriches
it in place: it adds `year`, turns each set into `{ label, songs }`, and gives every song a `slug`. It builds
`showsById` and `songsBySlug` (per-song show ids, deduped so a reprise counts once). All
queries are in-memory functions over those. Two derived facts live only here:
- **Encore labels are a heuristic.** The source has no encore flag, so a final set of 3 songs or fewer
  after at least one other set is labelled `Encore`.
- **Song identity is the slug** (`slugify(name)`). URLs, `?song=` filters, and song pages all
  key on it. The current data has no slug collisions; re-check that after a re-import.

`src/app.js` is thin routing over `data.js` and exports `app` without listening
(`src/index.js` listens), so tests can bind it to port 0. It also serves `public/` statically.
README.md has the API table.

**Front end (`public/main.js`)** is a hash router (`#/`, `#/year/Y`, `#/show/ID`,
`#/songs`, `#/song/SLUG`, `#/search?q=`). Each entry in `routes` returns an HTML string
that is written into `#view`. Every interpolated value must go through `esc()`. Tables use
`sortableTable(columns, rows)`, where each column is `{ label, cell, sort, num? }`. Sorting happens client-side
on each cell's `data-sort` value, ties fall back to the original row order (`data-i`), and one delegated
click handler on `#view` covers every table. Fetches use relative `api/...` paths.
